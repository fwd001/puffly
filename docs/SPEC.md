PUFFLY

Complete Product & Engineering Specification v1.0

«Puffly — Take a break. Skip the smoke.»

---

01. Product Definition

Puffly 是一个跨平台、低文字依赖、沉浸式的虚拟休息小游戏。

它的核心体验不是“阅读一个戒烟 App”，而是：

«打开 → 看到 → 直接操作 → 获得反馈 → 放松几分钟 → 离开。»

Puffly 将“抽烟休息时的仪式感”转化成一个无尼古丁、无真实烟草消耗的互动体验。

产品应该让用户产生：

«“哈哈，这个动作还挺像。”»

而不是：

«“我要先读说明书才能知道怎么玩。”»

---

02. Global Design Philosophy

第一原则：Zero Tutorial

默认情况下：

不提供教程页面。

不提供长篇文字说明。

不要求用户先学习规则。

第一次打开网站，用户应该能够仅凭视觉和直觉开始互动。

例如：

看到打火机
    ↓
自然会点
    ↓
看到烟
    ↓
自然会碰
    ↓
烟开始燃烧
    ↓
自然产生互动

游戏规则通过：

- 动画
- 物理反馈
- 声音
- 光影
- 手势
- 状态变化
- 微妙提示

表达。

05. Language Strategy

第一版 UI 默认：

«Language Independent»

不要让核心游戏依赖 i18n。

只允许少量非核心文字存在：

- Puffly
- 时间
- 数字
- 极短状态
- 一个手势动词（见 28 的例外）
- 设置中的必要项目

如果未来增加语言：

en
zh-CN
zh-TW
ja
ko
es
fr
de
...

只扩展外围 UI。

Game Core、游戏交互、游戏动画完全不依赖语言。

2026-10-05 补充（Smoke Ritual §9 落地）：

三层降级，顺序固定：目标语言 → English → 纯图标。

- English 是锚，不是翻译：每个 key 必须在它那里存在。
- 看得见的字可以一路降到“没有”（纯图标层），这是核心循环允许的状态。
- 播报给读屏软件的名字永远不降为零：§64 优先于审美。
- 中文量词（支/口/根/次）只出现在图鉴与档案里，主循环一个字都不带。
- 语言是偏好，不是状态机输入：`Settings.language` 由核心携带，核心从不读它（有守卫测试）。
- 界面随文字镜像（工作表从右边缘开始），场景永远不镜像：烟从左往右烧，
  回看一次录像（71）在任何语言下都必须得到同一条烟。
- 缺省跟随设备：没有明确选择时读浏览器的语言列表，读不到就落到 English。

2026-10-06 补：上面这些第一次有了**整表级**的判据（`apps/web/src/__tests__/copy-tiers.test.ts`）。
数出来的现状：锚上有 **139** 个 key，`zh-CN` 139/139 齐（表头那句"中文是完整的"此前只是注释），
`ar` 只有 **4/139**，占位符 `{n}` 一处不缺、也没有只在译文里出现的死 key。
**由这个数暴露出的问题**：语言行把阿拉伯语写作 `العربية` 摆给玩家选，而它背后只有 4 条字符串 ——
按 §9 回落到英文是设计，但用一个母语名去承诺一个 3% 的档不是。所以那一行现在把档位自己印出来
（`coverageOf()` 在 `i18n/index.ts`，行上渲染成 `4 / 139` 的数字，读屏名里也带上），
数字与柜内进度用的是同一个 `a / b` 形状，不新增字号。
三条判据各由一次单点变异打死：删一条中文 key → 红 3 条（缺 key / 中文该完整 / 只有 ar 未完成）；
把 `第 {n} 天` 的 `{n}` 弄丢 → 只红占位符那条；把那一格从行里摘掉 → 只红"这条答案确实渲染在语言行"。
**没有做**的：真把 135 条翻成阿拉伯语（表头写明那是译者的活，不在此处编），以及组件级挂载测试
（挂这张表要整个 `Puffly` 对象，本仓库目前没有那套脚手架 —— 所以"确实渲染出来了"这一条是结构判据）。

（2026-10-06 补充，按 Smoke Ritual `categoryTypes` 落地）"按住吸入"不是一种操作，而是三类：

| 品类 | 内容里的字段 | 手感 |
| --- | --- | --- |
| 卷烟 / 手卷 / 丁香（7） | `savourMs: 0`，`loadPerPuff > 0`，`exhaleMs: 0` | 按住多久就吸多满，次线性；每口给下一口留下阻力（余烬更亮、燃得更快）；吐就是一团 |
| 小雪茄 / 雪茄 / 斗烟（3） | `savourMs: 2000`，`loadPerPuff: 0`，`exhaleMs: 2500` | 含住两秒——进度环走的是这张嘴的曲线而不是时钟；不入肺，所以不留阻力；吐出来是缓缓的一口，寿命翻倍、初速减半、不再往上冲 |
| 水烟（1） | 三个字段全走吸入那一档，`loadPerPuff: 0.12` | 长会话低节奏：单支 50 分钟、口数更多、阻力留得最轻 |

四个字段都写进内容，核心不认"雪茄"这个词（§77）；pill 上的动词由这根烟自己的读数决定
（`readouts.savourMs > 0` → `含住 / savour`，否则 `吸入 / inhale`），家里只有一个地方知道这件事：
`ctaKeyFor()`。

判据：`packages/game-core/src/__tests__/savour.test.ts` 用同一支烟的两份内容做对照——含住的曲线在
500/1000/2000ms 上分别是 0.25/0.5/1 且不随时钟走；吸入的那条是次线性的前半段；吐出来的云按含进
嘴的量长；三口之后含住的负载是 0、吸入的 > 0.2；吐的那一团寿命翻倍、初速减半。把 `savourMs`、
`loadPerPuff`、`exhaleMs` 任一字段送进黑洞（改成常量），对应那一条必红——三次单点变异实测过。品类与抽法是不是同一件事，另有
`apps/web/src/__tests__/archive.test.ts` 双向钉住：`savourMs > 0 ⟺ kind === 'savor'`，11 根逐个走一遍。

（2026-10-06 补充，"烟没有还原那张图"这一条）把出厂的引擎 + 出厂的渲染器在真浏览器里离线跑一局
（时钟由脚本给，不靠 rAF——后台页面上 rAF 是 0 帧），把画布读回来量。**第一次量就把我的猜测打掉了**：
我以为病是"太亮太饱和"，同一套编排、同一粒种子对比，吐气峰值那一帧烟带里亮度 >220 的占比
改前 0.49% / 改后 0.50%、>250 是 0.03% / 0.13% —— **饱和根本没降**。真正变了的是**内部结构**：

| 吐气峰值那一帧（烟带内，同种子同编排） | 改前 | 改后 |
| --- | --- | --- |
| 亮度 >90 的采样数（云占多大一片） | 22999 | 9806 |
| 云内平均亮度 | 146.8 | 128.1 |
| 云内标准差 / 均值（相对起伏） | 0.234 | **0.294** |
| 相邻像素平均差（碎不碎） | 5.17 | **8.44** |

也就是说改前那是一团**均匀发亮的雾**铺在画面上半部，改后是一团**有明有暗、能看出片**的云。
配方上动的就是这一点：单片不再靠"不透明"堆体积，靠"片数 × 膨胀"。

| | 改前 | 改后 |
| --- | --- | --- |
| 单片峰值 alpha | 0.24 + 0.3i | 0.08 + 0.1i |
| 单片半径（写的值） | 0.03 – 0.105 | 0.018 – 0.055 |
| 一次片数 | 20 + 46i | 34 + 70i |
| 膨胀 scaleGrowth | 2.9 | 2.9（不动） |

判据分两层。单元层：`packages/game-core/src/__tests__/savour.test.ts` 的
"the breathed cloud stays see-through"钉住 alpha 上限与**到达**半径上限（`makeBurst` 会把写下的半径乘上
这根烟自己的 plume 系数与抖动，所以判的是发出去的值：写的 0.055 到达 ≈0.086，旧的 0.105 到达 ≈0.164，
线画在 0.12），并且同时钉"仍要膨胀 + 片数仍要多"——否则"更薄"可以靠"云更小"作弊通过。
把三个数原样改回去，全库 106 条里只有这一条红。
浏览器层：`tests/smoke/touch-device.mjs` 里新增"一口气是有结构的，不只是一片发亮"，
判的是烟带内的相邻像素差（5.17 → 8.44，线画在 6.5）与云内相对起伏，两者同时不达标才红。

复跑这套图：页面里 `import('/@fs/<abs>/packages/game-{core,renderer,content}/src/index.ts')` →
`createEngine({lighterId:'brass'})`（默认 wheel 有 6% 打不着，验图别用它）→ `createCanvasRenderer({...})`
→ **`engine.on((e) => renderer.handleEvent(e))`**（漏这一条粒子池永远是 0、画面上一条烟都没有——
本轮第一次就是这么被骗的）→ 每步 `engine.advance(1000/60)` + `renderer.render(state, 1000/60)`，
用 `canvas.getContext('2d').getImageData(...)` 读回来算。`renderer.particleCount()` 是"烟在不在池子里"
的直读探针，看图之前先读它。

**这一条还没有收口**：上面所有数字都只说明"更像一团碎开的云"，不等于"就是那张图"。
和 Ardot 那几帧的正面对比需要能看画面的浏览器（本轮内嵌页面切到后台后截图直接拒），
所以最后那一眼还是要你来定。

补一轮（同一份判据下量到的另一件事）：交接文档 §6.1 的皮肤表把**烟羽**列为皮肤的四层之一，
写的是"烟雾颜色与浓度"。实现里这一层只落到那层 density veil 上——`rgbToCss(tint, (density-0.45)*0.06)`
最亮处 alpha 也只有 0.033，等于没落。量法：给渲染器一份**只有烟羽不是原值**的调色板（其余三层从
未上色的视图里原样抄回来，这样任何像素差都只可能来自烟羽），跑同一个种子的一口呼气，
比较两次跑动里渲染器**逐个索取**的 sprite 颜色（按下标对齐）：改之前 **60 片里 0 片换色**。
现在烟羽在粒子出生那一刻就换掉烟雾类 burst 的颜色，材质类（`ember` 滤嘴、`ash` 灰、`impact` 托盘灰）
保留 core 写给它们的颜色——皮肤可以改烟，不该把灰改成蓝色。
判据：`packages/game-renderer/src/__tests__/plume-palette.test.ts`（4 条）。两条单点变异各自只红一条：
调用点不传 `plumeTint` → 只红"repaints the plume…"；去掉材质那道 kind 守卫 → 只红
"leaves the ash its own material colour"。另两条是防自证的正对照（两种候选色相距 >30）与确定性对照
（同一份调色板跑两遍 0 处不同）。

一个已知行为，不是缺陷：换皮肤时**已经在空中**的那片烟保留它出生时的颜色，几秒内自然散尽后整幅才统一。
粒子不带"我是不是烟"的标记，要做到瞬时必须给粒子加一个字段，为一次设置切换付这笔钱不值。

Ardot 那条路这轮走通了**读**、走不通**看**：文件在用户自己的 Chrome 里以只读身份打得开
（S1-S6 是 390×844 六帧，S3 吸烟 = 节点 `3:127`，S4 吐烟 = 节点 `3:187`），但整页 7% 缩放下
一帧只有 27×59 CSS 像素（截图里约 55×119 设备像素），烟羽本身不可辨。要放大必须真输入：
合成的 `keydown`（Shift+2 缩放到选区）
编辑器根本不收，`cua.keypress` 只吃 `{keys:[...]}` 且同样没生效，`cua.scroll` 会挂在一次等待确认的
输入授权上把整条队列堵死。所以"像不像那张图"这一眼仍然只能你来——把 S4 吐烟放大到 100% 对一眼即可。

**再补一条，这一条把上面努力的方向纠正了一半**：看到画面之后用户的说法是「像雾、没对上焦；设计稿里的烟
是有线条的，不用散开」。照这句话去量，病根不在片数、不在 alpha、也不在张角 —— 在**流场本身**。
`curl2(x, y, seed)` 的第三个参数选的是**另一张噪声格点**，不是同一张格点里的另一个位置，而粒子池把每颗
粒子自己的 `noiseSeed` 传了进去：紧挨着的两颗粒子被推往互不相关的方向，所谓"共享的涡旋场"其实从来不存在，
画面必然是一团失焦的雾。改成全场共用一张格点（每颗只留一个亚格点抖动），同一局同一时刻变成：

| 呼气在 2 秒时 | 每颗一份格点（出厂行为） | 共用一场（现在） |
| --- | --- | --- |
| 长宽比 σy/σx | 1.10（正圆 = 雾） | 2.40 |
| 横向 σx | 0.370 | 0.035 |
| 包围盒面积（舞台 = 1） | 3.47（三个半屏幕） | 0.14 |

静置烟柱在 3 秒：σx 0.193 → 0.009，长宽比 2.21 → 12.36。把 seed 换回每颗一份，形状判据当场红
（1 红 81 绿）—— 那是刚出厂的行为，不是我编的反例。
**上面这两组数（2.40 / 12.36 / 0.009）是当时的量具产出来的，那件判据现在已经换成了量整团烟，
所以它们只是历史读数，别再当今天的数引用**；今天的数在下一节，以及
`npx vitest run packages/game-renderer/src/__tests__/plume-shape.test.ts` 跑出来的那条。

**形状判据后来被证明量错了东西，这一条比上一条更重要。** 上面那张表里的"长宽比"量的其实是**跑了多远**：
一团云只要升得够快，它自己就会被拉成长条，跟它像不像烟无关。把整局烟雾真正画成一张图来看（把 renderer
一帧里真正 blit 的片数、位置、半径、alpha 全部录下来再合成），看到的是：2.5 秒那一帧里 698 个精灵只有
**50 个落在画面内**，其余全在屏幕外 —— 因为每支烟呼出的那口气在 **2 秒时就整体离开了舞台**（默认那支
classic：+2 秒位移 −1.06 个舞台高，+4 秒 −2.90）。用户说的"烟会到左上角""没还原 UI 图"，根子是同一个。

病根是一个常数：粒子池对**所有**粒子用同一个空气阻尼 0.9/s。烟是气溶胶，弛豫时间远小于一帧；烟灰是
2 毫米的碎片，0.9/s 差不多正好。同一个数必然对其中一个是错的，而对烟是错了一个量级 —— 终端速度
= rise / 阻尼，出厂值算出来是每秒 0.4～1.1 个舞台高，而烟头离画面上沿只有 0.37。

改法是把阻尼变成**粒子自己的属性**（`SMOKE_DRAG`，`MATERIAL_DRAG = 0.9`，按 burst 是不是
`ember/ash/impact` 分派），配方里 rise 的那些倍数一个没动，内容表里 11 支烟的 riseSpeed 一个没动。

**阻尼取多大不是拍脑袋，是被判据夹出来的。** 改 `SMOKE_DRAG` 之后
`npx vitest run packages/game-renderer`，读 `plume-column.test.ts` 打出的 `COLUMN@` / `THREAD@` 三行：

| `SMOKE_DRAG` | 那口气 +0.8 秒升出去多少（舞台高） | 烟柱 +3.5 秒 | 判据 |
| --- | --- | --- | --- |
| 12 | 0.069 | 0.187 | 2 红 —— 气还糊在嘴上 |
| 8 | 0.097 | 0.296 | 全绿 |
| 6 | 0.121 | 0.301 | 全绿，取绿的两档里最快的那一档 |
| 4 | 0.164 | 0.301 | 1 红 —— 摊得太开，`plume-contrast` 那条 5:1 不成立了 |

上一版这张表写的是"12 全绿、8 两红、6 四红"，那三个数在当时是真的，现在不成立了，原因是
`SMOKE_DRAG` 不再是唯一那个数：一口气原本作为**一次** burst 在同一瞬间全部出生，阻尼一降它就变成
一团整体平移的小疙瘩 —— 用户那句"像雾、没对上焦"在 12 这一档上换了个形式回来了，不是散开，
是根本没长开。把出生摊开是另一半，见下。

**一口气不是一瞬间。** `intake.ts` 给每颗烟一个 `delay`：burst 里第 i 颗要等 `窗口 × i/n` 才出生，
出生前不动、不老化、alpha 为 0，所以画面上什么都没有。窗口按 kind 给 —— 呼出 0.3 倍自身寿命
（classic 约 1.1 秒）、含住 0.25、静置 drift 0.12，上限 1.6 秒。为什么不是一个数通吃：drift 每几百
毫秒就来一团，把一团摊满一秒多，它就不去补上一团留下的那段空，反而把烟柱自己拉稀 —— 实测
`long` 那支的断点从 0 涨回 5。最后出生的那颗同时暗一半（`STREAM_TAPER`），所以这口气是先重后轻
吐完的，不是一根等亮度的柱子。

**烟柱横向比纵向听话。** 阻尼降到 6 之后横向漂移顶到 0.094 个舞台宽（判据 0.05）：curl 场是
**房间尺度**的（八个格子跨一屏），照单全收等于把一柱比空气重的烟当成一粒示踪尘。
`LATERAL_SWING = 0.45` 只折横向那一半。

**"越往上越薄"得写在配方里。** `makeBurst` 以前对所有 kind 一律摇 `alphaDecay ∈ [0.55, 0.95]`，
那是给一团灰用的；现在 exhale / puff / drift 各自写死（1.9 / 1.1 / 1.25），材料类继续摇。
那一抽随机数照抽不误，所以 §71 的回放序列没有整体错位。

判据这轮换了口径的有四处，每处都留着"为什么"：

- `plume-column.test.ts`（新增）在**合成后的帧**上量一条线：从烟头往上，亮体伸出去多远（extent）、
  中间有多少行真的亮着（fill）、中位宽度多少（width，防"用雾换高度"）。旧阻尼下实测
  extent 0.059、嘴边上六行只剩 2 行亮 —— 一个飘起来的小疙瘩，不是柱子。
- `plume-on-stage.test.ts` 不再要求"+2 秒整团在画面内"。出烟点离上沿只有 0.42 个舞台高，任何
  一根柱子在 4 秒时中心都会越线，"越线之前必须先淡到看不见"这条**没有任何上升的烟柱能满足**，
  它唯一能逼出来的就是不许上升 —— 也就是这一整轮开始时要治的那个疙瘩。现在钉的是：+1.2 秒整团
  95% 在画面内（治"整团飞走"）、+2 秒中心还在画面内、+4 秒横向离开出烟点 ≤ 0.05（治"跑到左上角"）。
- `plume-continuity.test.ts` 的圆盘半径补上了 `renderer.ts` 自己的 `PUFF_SPREAD` 与景深系数。
  它注释里写着"量 `drawSmoke` 真正 blit 出去的半径"，代码里却把这两个乘子漏了，于是量到一根比
  画面里窄三成的柱子，把它的 1.3 倍当成断点报红了 2 支烟。常量从 renderer 导出、判据 import 它，
  两边不再各写一遍。
- `savour.test.ts` 的"更满的一口吐出的烟更多"改成 21 根烟取中位。§16 给每团 burst 的颗数 ±55%
  抖动，而这两口的设计差只有 1.49 倍 —— 各摇一次再比大小，量的是抖动不是设计。
- `plume-continuity.test.ts` 只收 `kind === 'drift'`。把 ash / ember 混进这团点云里量，往下掉的
  烟灰会把一根完整的柱子读成 0.21 的覆盖率 —— 上一轮对着合成图说"烟柱断成一串珠子"，说的就是
  这个被误读的量。

**11 支烟的脾气没有被这几个数抹平。** 阻尼、窗口、摆幅都是共用的一套，但每支烟的 `riseSpeed` /
`dispersion` / `turbulence` 仍来自内容表，快慢垂帘的差别由 `aliveness.test.ts`（六次相同的手势
必须吐出六口不同的气）和 `stage.test.ts`（两支烟的呼出在 spread / turbulence / rise 上必须可分）
钉着，这一轮没有动过它们。

**这一轮最贵的一条不在烟里，在测试脚手架里。** `harness.ts` 的 `lit()` 固定 `run(900)` 就认为点着了，
900 毫秒是夹具那支打火机的时间，不是内容表里 11 支的。用 `DEFAULT_CONTENT` 时 `lit()` 返回的状态是
`LIGHTING`，而 `beginPuff` 只从**已点燃**的状态起手 —— 于是 press 被静默吞掉、release 结束不了任何一口、
exhale 一个都不发。`plume-on-stage` 里那句 `if (!burst) throw 'never breathed'` 是唯一会响的铃，
而它此前不响，是因为旧阻尼把 RNG 流停在了一个刚好赶上的落点上。`lit()` 现在等到真着为止（等不到就
大声失败），全仓 53 个调用点共用这一处。修好之后回头看：那四份"量一口气"的 renderer 判据，
一直在量一根没有呼吸的烟。

方向改回来时撞到两条旧判据，两条都改了口径而不是删数：`savour.test.ts` 里"还必须鼓起来
（`scaleGrowth >= 2`）"是上一轮的错误结论，它真正要防的"更薄不许只是变小"现在由形状判据来防；
`rendering.test.ts` 的"风是速度不是加速度"现在先把湍流设成 0 再量，否则量到的是共享流场在两池之间的
差异，不是风。

22. Micro Events

大多数事件必须非常小。

例如：

窗外灯光闪过

风吹过
烟雾突然旋转

用户可能甚至不知道这是系统事件。

这正是目标。

（2026-10-06 补充）"非常小"也包括**没有事件的时候**。风的风向扰动和烟的湍流原本是每帧重摇一次骰子，
60 Hz 下这就是一条没有来由的高频抖动——玩家不会说"骰子在响"，他只会说背景一直在晃。现在那一次抽样
仍然每帧照做（§71 的取数次数不许变，见 ARCHITECTURE.md「Determinism and replay」），但它是 `approach()`
的**目标**而不是字段的**值**：`windGust` 以 0.45/s、`turbulence` 以 1.1/s 追上去。

实测（同一粒种子、点着后取 30 秒里所有"没有任何事件在跑"的相邻帧）：

| | 每帧最大跳变（修好） | 每帧最大跳变（每帧重摇） |
| --- | --- | --- |
| `world.wind` | 0.00064 | 0.159 |
| `world.windDirectionDeg` | 0.0051° | 1.27° |
| `smoke.turbulence` | 0.0033 | 0.311 |

浏览器里也量到同一件事：真机上取画布上方 30%×18% 那块纯背景，逐帧 RGB 平均绝对差，
每帧重摇是 **0.150**，平滑后是 **0.033 / 0.019**（两次独立复跑）——"晃"在像素上是 4.5 倍。

判据：`packages/game-core/src/__tests__/stillness.test.ts` 四条，每条只被一次单点变异弄红——
去掉风的平滑 → 只红"相邻帧不许跳"那条；去掉湍流的平滑 → 只红湍流那条；把平滑速率改成 ≈0（冻住）→
只红"风仍然要走"；把湍流钉成常量 → 只红"烟仍然要卷"。后半组是必要的：只判"不许动"会被一个死掉的世界
满足，而 §21 明令禁止那种世界。测量刻意跳过有事件在跑的帧并在断点处断开，所以事件自己的起止不会被
读成跳变（它们本来就已经按 sin 包络进出，§59）。

**同一句抱怨（「刚开始是不怎么抖，然后后来就一直抖抖抖抖」）还有第二个来源，而它不在核心里。** 风和
湍流修平滑之后，画面上仍在抖的那半是**雨**：`weather.ts` 把每条雨线种子成 0.02..0.07 stage（手机上是
25 px 起）长、每帧走 11..22 px——相邻两帧几乎不重叠，眼睛看到的不是往下落的水，而是一堆在原点闪现的
短划。它只在天气是雨的时候出现，所以"后来才开始抖"。现在是 0.07..0.15 长、0.46..0.72 速：每帧
7.1..9.6 px。

浏览器里用真实像素把这两组常数对量过一次（同一批种子：把新参数反解回那两个 fbm 值，只换仿射变换），
`PROBE=/tmp/puffly-wob/rainpx.js PAGE=http://localhost:5175/ node run3.mjs`：每帧被重画的墨迹占全部墨迹
**0.728 → 0.400**，单像素峰值跳变 **106 → 72**，最短那条线 **25 px → 72 px**。

应用内也复看了一次（`/tmp/puffly-wob/drift.js`：同种子同钟点，三个时间窗里天气都确实是 `rain`）：天空那块
每帧平均墨迹 **0.52 / 0.64 / 0.67 → 0.17 / 0.46 / 0.47**，最坏单像素跳变 **219 → 140**。两次跑之间一共
落地了三处改动（雨、火星 presence、阴影与灰尘），所以这组数只是**佐证**，归因以上面那条只换两个常数的
A/B 为准。改前改后都还剩 ~134 的峰值，那不是抖：1 px 宽的雨线以 alpha 0.256 压在暗天上，扫过一粒像素
本身就是三通道相加约 150 的变化 —— 那是要的运动。

判据：`packages/game-renderer/src/__tests__/rain-fall.test.ts` 三条——单帧位移 ÷ 线长 < 0.4（实测最差
0.124）；每帧像素落在 2..14 之间（冻住会红、抖回去也会红）；最后一条不读生成器，而是从 `drawRain` 真正

### 22.y 通风系数：地方第一次改变烟本身，而不只是颜色（2026-10-07）

设计稿（PPT 第 24 页「吸烟场所 · 12 个场景」）给这一条的原话：

> 通风系数 0.0（完全密闭·厕所/楼道）— 1.0（强对流·户外墙边）。系数决定烟雾 alpha 衰减速率与扩散半径。
> 同一个烟种在 0.05 与 0.90 的场所里可见度差 4 倍。这是本机制存在的唯一理由——它比换皮肤更能建立在场感。

落地方式是把"系数"当成**场所的一个事实**，不是渲染器的一个开关：

1. `Environment.ventilation`（内容字段，§77：新地方就是表里加一条，不需要动核心）。
2. `ventDraught(ventilation)` 在 `game-core/systems/smoke.ts` 里是**唯一的换算家**，两头都从它取数：
   核心的 `smoke.visibility`（还有 audio）和渲染器的 `spread`（半径）。刻度按稿子自己点名的两端来定，
   **不是从 0 开始**——`0.05 → 0`、`0.90 → 1`，密封端就是"烟还是校准那天那个样子"。这条是硬约束：
   本仓库所有烟柱半径与 alpha 都是在屋里校准出来的，如果系数从 0 起算，任何一个默认房间都会先被扣掉
   一刀。单因子实测（§57 的对比度，HEAD = 5.09）：只有 alpha 那半被扣时 **4.89**，再叠上"半径也跟着缩"
   时 **4.13**（当场红）——也就是说贵的那一半是半径，不是亮度。
3. alpha 那一半留在核心（`1 - draught * 0.75`，端点正好 4.00×）；**扩散半径那一半刻意不写进
   `smoke.dispersion`**——那是烟种自己 authored 的倾向，且从来没有像素读者；把场所乘进去就是"半接线的
   字段"（编译过、判据绿、产品里是零）。半径只在渲染器 `renderer.ts:304` 花一次，且只加不减。

实测（同一间 quiet-room、同一支 classic、同一 seed，只动通风）：

| --- | --- | --- | --- |
| 0.05（密封） | 0.6288 | 10.38 px | 0.0242 |
| 0.90（强对流） | 0.1572（**4.00×**） | 15.07 px（**1.452×**） | 0.0145（0.60×） |

**稿子里没有"网吧"**——用户口语点名的那一处在 12 格里找不到，需要他确认要不要额外加。

判据：`apps/web/src/__tests__/scenes.test.ts` 八条——七间房一间不丢也不重复（`byRung` 的 id 集合与

（2026-10-06 补充）"不像机械按钮"最狠的一处是**按住吸入那一段**——它不是事件，是一条持续 1–2 秒的
bed，玩家真的会听见它。原来它是"粉红噪声过一个 460Hz 带通"，一条宽带通 + 一个 0.32Hz 慢摆。
把生产侧的 `createAudioEngine` 接到 `OfflineAudioContext` 上离线渲染 2 秒（同一个引擎、同一份配方、
只把 autoplay 那个 state 标志包一下——offline 上下文永远不会报 running），量出来是：

| 吸入 0.85（同一粒种子） | 谱心 | 1.5k 以上 / 150–900Hz 之比 | 谱通量（自己动多少） | 峰值 |
| --- | --- | --- | --- | --- |
| 改前（一个带通） | 2111 Hz | 4.39 | 12.07 | 0.058 |
| 改后（管 + 抖 + 胸） | 1440 Hz | 2.02 | 16.23 | 0.080 |

诊断不是"不够亮"，是**没有下半身**：4.4 倍的高频比就是"吹风机"三个字的形状。所以加的不是高频，
是三段里的第二段和第三段：

- **管（duct）**：一个 `peaking` 挂在 body 之上（1.9kHz、Q0.9、+3dB），中心频率由引擎跟着用力走
  （`1450 + intensity*820 + density*150`）。**必须是 peaking 不能是串联 bandpass**——串联会把想强调的那段
  自己饿死，实测那样反而更暗（谱心 2114、但 19:1 的头重 + 48% 的响度是另一条走错的路，+9dB 那次）。
- **抖（flutter）**：7.3Hz 与 17.9Hz 两个不成整数倍的正弦去摇那根管（±260 / ±90Hz）。通量 12.07 → 16.23
  就是它。**摇的是管的频率，不是 bed 的 level**：LFO 是"加"到参数上的，而引擎会把 level 驱动到 0——
  挂在 level 上就等于一根不吸的时候也在呼吸的烟（这条有专门的判据）。
- **胸（rumble）**：一路并行的 brown 噪声过 300Hz 低通，`gain 0.28`，汇到 level 旁边而不是前面。
  0.55 那一次把整条 bed 压成 907Hz 的闷响，0.28 是把 2.02 这个比解出来的。

判据：`packages/game-audio/src/__tests__/draw-voice.test.ts` 四条，五次单点变异——去掉 formant 目标只红
"管会随用力收紧"；去掉 flutter 只红"两个不成整数倍的速率"（它同时弄红下一条的正对照，那是设计）；
去掉 body 只红"并在旁边而不是穿过去"；往 level 上挂一个 LFO 只红"静音的 bed 不许呼吸"。
**第五次（把 body 的 loop 排除在 re-seed 之外）一开始活了下来**——`beds.test.ts` 那条
`>= loopsBefore + 5` 挡不住它，于是把这条判据搬到它声称的地方（数喂进 `bed.draw.draw:rumble` 的 loop
源在 20 秒后必须不止一个），现在它会红，且只红 body 那一条。

顺带修掉一个真 bug：`BedController.sync()` 是**手抄字段**重建 target 的（`{ gain, cutoff }`），
所以新加的 `formant` 算好了、接好了、然后在到达图之前被丢掉——和 storage 那几个
`readSettings/cloneProgress` 逐字段重建的坑是同一个形状。现在改成展开 + 只覆盖 trim 碰的那一个。

**用户听后说"偏亮"。量下来病不在整体明暗，在那根管子的落点。** 用同一把离线尺子（`OfflineAudioContext`
渲染出厂那条链，再用 26 个对数分布的 Goertzel 探针取带能量）量：把 2.4 kHz 的能量对 900 Hz 的身体比，
旧配方是 **3.82**；把 duct 从 1900 挪到 1200、运行时 formant 从 `1450+820i+150d` 改成
`950+330i+90d` 之后是 **2.97（静止）/ 2.48–2.73（一口之中）**。抖动按同比例缩（260→170），
所以 shimmer 0.61 → 0.62 —— 颤动没被顺手抹掉。

这里有一条判据教训值得单独记：原来那条"formant 必须 < 2400"的线，比它要拦的出厂值 2379 只高了
21 Hz。**画在现有值头上的线什么都拦不住** —— 它绿了整整一轮，而声音一直是亮的。现在收到 1500
（2.4 kHz 那条"亮"带之下），并补一条"抖动深度不超过 duct 基频的 15%"：把基频调低这件事本身
会让同样的绝对深度相对变尖，这两件事必须一起看。

（2026-10-07 补充）用户接着说"默认的燃烧的声音太刺耳了，淡一点"。**同一把尺子量到的是同一个病，
在另一条 bed 上。** 燃烧声是 ember bed，它只有一层 —— 默认那支烟的配方里只有 `crackle` 进了这张床
（`BED_VOICES.ember` 收 crackle/ember/ash，draw-warm 只给了 crackle）。而 `crackle` 的 shape 是
**1100 Hz 高通**，`bedTargets.ember.cutoff = 300 + ember*1200` 又随烟头变亮往上推：一支点着的烟
90% 的时间停在 brightness 0.918（跑真引擎 4000 步量出来的分位数），于是高通拐点被推到 **1402 Hz**。
"越热越开放"这句话写在低通上是对的，写在高通上就是"越热越没有下半身"。离线渲染整局静止状态：
谱心 1756 Hz、1.5k 以上对 150–900 之比 **2.41**、峰值 0.0361、波峰因数 31.9 dB —— 500 Hz 以下
几乎没有能量。刺耳说的是这个洞，不是音量。

**第一个解法被量出来的数否掉了。** 照吸入那条床的样子补一路 brown 噪声 `rumble`：增益从 0.3 一路
降到 0.035，250 Hz 以下始终占 42%～63% 的能量，每一个截止频率都一样 —— 稀疏颗粒带在低频上根本
竞争不过宽带棕噪声。那是另一个毛病，不是这个。真正的解法是把带放到身体里去：shape 改成
**620 Hz 宽带通（Q0.6）**，ember 的 cutoff 改成 `640 + ember*430`（静止 1035）。同一把尺子重测：
谱心 **596 Hz**、高频比 **0.07**、峰值降 39%、波峰因数 27.2 dB，**rms 几乎没动**（0.00091→0.00101）
—— 淡的是edge，不是声音本身。

判据：`packages/game-audio/src/__tests__/burn-voice.test.ts` 三条，三次单点变异各自只红该红的那条
—— 把 shape 改回 highpass 只红"它的旋钮只会往开拧"；把 cutoff 改回 `300+1200e` 红"停在身体里"和
"越热越开"两条；把 cutoff 压到 `180+120e`（闷成嗡声）只红"停在身体里"的下界。

**这一轮的量具本身错过两次，两次都值得记。** 一次是量具用桩 RNG：`grain` 噪声的颗粒位置取自
`rng.next()`，桩里写成常数 0.5 就生成出一张**没有颗粒**的缓冲，谱心 454、身体 82%，看着自洽全是假的
—— 同一页里跑真引擎（谱心 193）和床（454）对不上，才发现的是尺子。另一次更早就埋下：
`createProfileStore` 拿到 `DEFAULT_CONTENT` 时抛在 `engine.guard()` 里被吞掉，引擎从此静默标死，
渲染出来是一片零 —— 和"声音太小"长得一模一样。**离线量声必须先看 rms 不是 0**，否则零和安静分不开。

（2026-10-07 补充）用户说"冒烟的位置好像没有跟燃烧的位置重合，应该是从燃烧的那个点出来"。**根因是
`px()` 各向异性，而画烟杆用的是各向同性的变换。** `viewport.px()` 把归一化 x 乘 `stage.width`、
y 乘 `stage.height`（390×844 手机上就是 390 和 844 两个尺度），而 `drawCigarette` 用
`translate(px(pivot)) + rotate(pose.angleDeg) + len(pose.rodLength)` 画杆 —— 一个圆变换画进一个椭圆
空间。于是归一化空间里作者写的角度和长度，过了 `px` 之后既不是屏幕上的角度也不是屏幕上的长度。
`pose.tip`（= `anchors.ember` = 每一团烟的出生点 = 命中判定的中心）走的是椭圆那条路，画出来的烟头走的是
圆那条路，两者在 390×844 上差 **52 px**：烟从杆旁边半米的空气里升起来。

真浏览器里量（真 engine + 真 renderer + 真 canvas 2d，取全画布最亮像素当画出来的烟头）：
改前最亮点 (355, 340)，映射后的 tip (317.6, 311.6)；改后最亮点 (317, 308)。

**修法是把杆的坐标系交给 core 已经认可的那两个端点**：`translate(px(pivot))`、
`rotate(atan2(px(tip) − px(pivot)))`、长度取这两点的像素距离；灰柱长度同理取
`px(ashTip) − px(tip)`，不再各自 `len()` 一遍。可见代价是杆在屏幕上的角度从 −17° 变成 −34°
（映射之后的真实角度）—— 这不是新引入的失真，是这套归一化布局一直以来的约定：
`stageDistance(a, b, aspect)` 早就在按 aspect 修正，命中判定从头到尾都活在这个模型里，
只有画的那一边没有。

判据：`packages/game-renderer/src/__tests__/rod-anchor.test.ts` 四条。一次单点变异（把画杆改回
`rotate(angleDeg) + len(rodLength)`）红两条：角度差 0.284 rad（16.3°），画出来的远端离出烟点
31.5 px。第三条断言额外要求"归一化角度和屏幕角度在这里确实差 0.1 rad 以上"，否则这条判据在方形窗口上
会白拿一个绿。

**为什么前几轮"看图"没看见**：那几张图是软件画布渲的，它不画 path —— 烟杆、烟灰缸、打火机在图里根本不存在，
所以"烟和烟头不重合"这句话在那张图上**不可能**被发现。量的是烟，看的也是烟，画的东西有没有对齐从来没进过视野。

（2026-10-07 补充）同一件事第二次逼出来的：这一轮的看图换成了真像素（headless Brave + CDP），第一次看见
打火机原来是一节**圆柱**。旧画法把"盖"画成与机身等宽、共用同一道渐变、顶上一条通宽高光的矩形 ——
玩家读到的是"一罐东西"，不是打火机。现在按翻盖打火机重画：机身 / 烟囱 + 灯芯 / 略宽一层的盖（盖是**套在**
机身上的，那道悬出才是"这块会掀开"的轮廓线索），加铰链凸点与滚花火石轮。
两个画法上的坑值得记下来，因为它们都不是"细节不够"：

1. 盖**不能**绕左边缘在画面平面里旋转（那是门的转法）。铰链在机身的**后**沿，正视图里盖是朝远离镜头的方向
   **倒下**：投影变矮、远边收窄、露出自己的**内壁**。第一版按门画，图里出现的是一块斜着插出去的板。
2. 火焰的底**不能**用 `top`（合盖时机身的顶）。盖掀开之后灯芯比它低 13px，火像是从空气里长出来的；
   而火焰路径若从机身等宽处起步，`lighter` 混合模式下盖的内壁会把火根烧成一个**白盘子**。
   现在 `flameBase = chimTop − 0.05·bodyH`，且底宽收到 `0.2·bodyW`（火从灯芯出来时最窄）。

`lid` 是状态而不是画法，因为图、点击声、以及后面要做的空闲小动作必须对"什么时候是开着的"取同一个值。
判据：`packages/game-core/src/__tests__/lighter-cap.test.ts` 三条（桌上是关着的 / 开盖**早于**火起来 /
松开后落回去并且不再自己起来）。三次单点变异各红一条：钉死在 0 → 第二条；把开合两个速率对调
（`engaged ? 5.5 : 13`）→ 还是第二条，因为这时盖落在火后面，画面上就是火隔着盖子烧；
关闭速率改成 0.05 → 第三条。

## 6.2 房间也可以由玩家自己上色（2026-10-07）

「背景也可以作为自定义」这一条落在**设置**里而不是**皮肤**里，理由是：皮肤是要解锁的收藏品，
而"我想让这个房间是什么颜色"是一个决定，不该有门槛。所以 `Settings.customBackground:
ScenePalette | null`（四层：天空上端、天空下端、地平线、前景剪影），走的是 `skin` 那条完全一样的路
（`rendererSettings()` 一处组装 → `RendererSettings` → `applyBackground()` 与 `applySkin()` 并排）。

三条不变量，都是照 `skin.test.ts` 的形状钉的（`custom-background.test.ts` 四条，三次变异各红
1 / 1 / 2 条）：
1. 只改这四层。`background.kind` 决定画面里有没有那道楼梯，`fog`/`grain` 是空气 —— 一个颜色选择
   能改到它们，就等于颜色变成了地形。
2. 不许碰任何可被度量的数字（`environment.background` 之外整个视图逐字段等值）。
3. `null` 时**返回同一个对象**而不是副本：没接管房间的游戏不应该每帧为这个可能性分配一次。

**一半的调色板比没有更糟**，所以存储侧 `readScenePalette` 的规矩是：四层里任何一层不是
三个 0..255 的数，就整块退回 `null`（并在 `errors` 里点名是哪一层），而不是画出"三层是玩家选的、
一层是出厂的"那种看起来像 bug 的房间。能夹住的（-40 / 300.6）夹住，读不出来的（NaN、字符串、
数组）整块作废。`cloneSettings` 为此多抄一层 —— 别的所有设置都是标量，浅拷贝就够。

**取色器打开时填的是"你现在站的这个房间"**：`Puffly.sceneColours()` 从当前视图读那四层，
所以玩家第一次按下开关看到的是四个已经是他刚在看的样子，而不是四个黑块。
真机（headless Brave + CDP，`localhost:5175`）量到：`[data-setting="scene"]` 存在、
按下前 `aria-pressed="false"` 且色块行 0 个、按下后 4 个 `<input type="color">`，
值依次是 `#222124 #34302c #423c38 #181719` —— 正是 quiet-room 的 sky[0]/sky[1]/horizon/silhouette。
同一把尺子下，把 `customBackground` 交给渲染器之后整帧平均 RGB 差 **79.7**、
32.9 万像素里有 **32.3 万**个变了：这确实重画了房间，不是只改了一个设置项。

### 60.1 打火机可以被把玩，也可以被要求别动（2026-10-07）

两处各自都对、合起来是"死按钮"：`handleTap` 的 `case 'lighter'` 只在 `PICKED_UP / IDLE` 下
`engageLighter`，烟已经着了以后再点它就一个 `break`；而一张永远不会自己动的桌子是照片不是房间。
现在 `lighter.fidget`（0..1 冲量，自己衰减完）同时接这两件事：**玩家闲点一下**，和
**没人理它的时候它自己偶尔来一下**（`settings.idleFlourishes`，默认开）。
`fidget` 是冲量而不是模式，所以一次耍帅会在 620ms 内自己落回去。

渲染上 `fidget` 让机身上跳 `0.22·bodyH`（`sin(π·fidget)` 起落），盖由 `fidget > 0.4` 与
`engaged` 共同点亮 —— 盖不需要知道这次是手弹的还是自己弹的。跳变写在锚点上而不是
`ctx.rotate`，因为 `prop-placement` 那条判据读的是函数发出的绝对坐标。

**加一条自己的骰子之前先想清楚代价。** 第一版 `tickFlourish` 里写了 `rt.rng.next()`，
639 条测试当场红 4 条，其中三条（烟的连续性、烟柱形状、整局渲染）跟打火机毫无关系 ——
那一步多出来的骰子把后面每一颗粒子的随机数都平移了。改成**读上一步已经摇出来的
`lighter.flicker`** 当作散布源（不新增取数），四条同时回去。
§71 说的"取数次数"就是这个意思：**开关只改变发生了什么，不改变问了几次骰子。**

判据 `packages/game-core/src/__tests__/lighter-fidget.test.ts` 四条，四次单点变异各红一条：
`else fidgetLighter` 删掉 → 红"闲点要有回应"；`idleFlourishes` 那行早退删掉 → 红"关掉就该全静"；
`FIDGET_MS` 改成 9,000,000（冲量不衰减）→ 红"一次把玩是几帧不是一种模式"；
把散布源换成 `Math.random()` → 红"同一张桌子重放两次结果一样"。

顺带把这条开关接到设置表里（`data-setting="fidget"`，✦）。文案只补了 en 与 zh-CN：
`copy-tiers.test.ts` 要求 **`ar` 必须是唯一那一个"未完成但有标注"的层级**，
给它补一条反而会把那条判据写死的那个 `['ar']` 弄红。

### 音频 55.5 把烟拿起来这件事以前是没有声音的（2026-10-07）

### 音频 55.6 桌上看得见的那只烟灰缸，声音里必须也有它（2026-10-07）

「声音一定要跟画面连接，画面切换声音要立即切换」这一条量出来两处断点：

1. **四只烟灰缸在声音里是一只。** `profiles.ts` 的 `stateId()` 根本没有 `tray` / `extinguish` 两个
   role 的分支，直接 `return undefined` ⇒ 每次都走 `byPrefix('tray')` 拿到内容表里**排在前面的那条**。
   而内容表里 `tray-stone / glass / tin / porcelain` 是四条**不同**的配方（石头不响，其余三只
   各自以不同增益/音高散布响）。画面换了，声音没换。
2. **烟灰缸的身份从来没进过视图。** `style.ashtray` 只有三个颜色，`stage.layout.ashtray` 只有位置，
   没有 id。所以这不只是"音频少读了一个字段"，是核心根本没把它交出去。

补法：`AshtrayContent` 加 `extinguishProfileId`（磕灰与掐灭是两件事，材质对两者的影响不同），
`GameState` 加 `ashtray: { typeId, soundProfileId, extinguishProfileId }`，`selectAshtray()` 与
`style` 一起更新（**同一个动作里一起改**，否则颜色和声音会有一帧分家）。

判据 `packages/game-audio/src/__tests__/picture-and-sound.test.ts` 三条，四次单点变异分别红
2 / 1 / 1 / 1 条：`stateId` 退回 `undefined` 红前两条；ambient 钉死成一条红第三条；
内容里两只烟灰缸共用一个 `extinguishProfileId` 红第一条；共用一个 `soundProfileId` 也红第一条。

**这一轮自己写错判据两次，都记下来：**
① 一开始 `TRAYS` 是我在测试里**手抄**的四条，于是"两只共用一个 id"这个变异**全绿** ——
判据读的是抄件不是出厂表。改成 `DEFAULT_CONTENT.ashtrays` 之后那条变异才红。
② 第二条界先写成"四只的**音色集合**要互不相同"，实测玻璃/锡/瓷三只都是 `ash+chime`，
差别在增益与音高散布上 —— 那是内容合理的写法，不是缺陷。改成比**整条配方**
（`voice:gain:pitchSpread`）并要求"恰好一只不含 chime"。

顺带量到并**排除**的一条：`profiles.ts` 的 `cached` Map 从不失效，看着像 bug，其实不是 ——
它的 key 是 `role|wanted`，换选择时 `wanted` 变了就是新 key。真正会漏的是上面那个
`wanted === undefined`，而它已经被这三条判据钉住。

### 音频 55.7 火星的抖动有人读了，两个"只响不动"的世界事件接上了画面（2026-10-07）

第 4 条剩下的两处断点，形状不同但都是"画面与声音各读各的"：

**一、`ember.flicker` 每帧算出来没有任何人读**，而"这根烟现在多亮"在五个地方各写了一遍，系数还三个样：
核心 `tickEmber` 用 `flare * 0.45`、音频两处 `* 0.5`、`props.ts` 两处 `* 0.5`、烟晕 `* 0.6`。所以每处
都自洽，合起来没有一处是别人的答案。收成 `emberPresence()`（在 total 上叠 ±8% 的呼吸），五处消费者
一起改读它；`tickEmber` 决定 `lit` / `temperature` 时**仍然用不抖的那个 total** —— 着不灭不能取决于
一次骰子（§71）。音频切片因此多了 `flicker` 字段，按编译器数只有一处构造点需要跟。

判据 `tests/ember-and-burn.test.ts` 四条，落在**能同时看见两个适配器的层**：burn bed 的目标值在五个
flicker 上等于 `emberPresence`（12 位小数）、图确实追上了它（bedLevel 0.6440 → 0.7560）、整帧墨迹按
presence 走（每单位 +2.946）、以及一条源码扫描——两个适配器里不许再出现自己那份 `ember.brightness +`
推导（带阳性对照）。四次单点变异分别红 2 / 3 / 2 / 2 条。**这轮判据自己错过一次**：图片那条起初写成
"所有渐变 alpha 之和随 flicker 上升"，于是把两处画法退回旧推导后**仍然全绿**（一处服从就够了）；
钉成比值才有判别力。

**二、`SHADOW_CHANGE` 与 `SMOKE_SWIRL` 写的两个字段一个读者都没有**：事件来了、`room` 响一声、画面
一动不动。先把量级量出来（不是"大概是小事"）：出厂内容上 `world.shadow` 能到 **0.30..0.77**，
`smoke.turbulence` 跨 **0.01..4.94**。
- 阴影按仓库自己已有的先例处理——雨就是把房间亮度乘 0.72 折进 `light.ambient`——阴影也折进去，
  份额 `SHADOW_SHARE = 0.7`。这样一个字段被读的八处（天空、窗、地面光斑、散景、道具主光、灰尘…）
  一起暗下去，而不是给渲染器再添第九处"记得这里也要减"。`types/state.ts` 里那句注释写明：
  折进过了，下游**不许再减第二次**。
- 旋折给**灰尘**：`drawDust` 的摆幅乘 `1 + clamp01(smoke.turbulence) * 0.6`。**烟柱本体不动** ——
  那个字段在 12 支烟上跨 0.01..4.94，折进流场等于把所有烟的形状重新调一遍，而形状正被别的判据钉着。

**"画面上真的暗了"这条差点量错地方。** 先量天空第一个色标：满阴影只让它 37,37,39 → 34,34,36，
看着像折进没生效。其实这套设计就是近黑、且曝光有 0.34 的下限，天空本来就不许被调亮；真正看得见的是
**暗角收拢** 0.748 → 0.819。判据改成量那一个，另留"天空不许变亮"作为方向断言。核心侧则是两头一起钉：
没有事件的帧 `ambient == resolveLighting()` 的基线（误差 1e-6），有阴影的帧等于 `base * (1 - shadow * SHADOW_SHARE)`
（实测 0.340 → 0.292，shadow 0.203）。

判据 `tests/world-and-picture.test.ts` 三条，三次单点变异各红自己那一条（阴影不折进 ambient / 灰尘不读
turbulence / 暗角不再跟 ambient 走）。

**仍然没做，并且这次判断为不做**（第 4 条最后一处）。先把数数对：`WorldEventId` 有 **10** 个，
`WORLD_CUE` 给它们 **6** 种 cue（wind / rain / ash / ignite / room / sputter），并没有"全都共用一个
`room`"这回事 —— 落进同一个 `room` 的是其中 **5** 个：旋、环境噪声、光变、阴影、ambience。
本轮之后这五个在画面上各有自己的反应（旋摆灰尘、噪声抬烟尘可见度与房间增益、光变亮窗与散景、阴影收暗角），
剩下的是"五件事发五种声"。§22 要的是这些事**不该被注意到**（玩家只该看到烟自己动了），把它们拆成
五种可辨认的音效会直接和那条打架 —— 那是给背景加解说。所以这是一条有意保留的合并，不是欠账。

**「画面切换声音要立即切换」里的"画面切换"到底指什么，也查清了。** 局内没有"换房间"这条路径：
`environmentId` 在 `createEngine` 时随选择一起定下（`apps/web/src/composables/usePuffly.ts` 里
`createEngine({ … environmentId: selection.environment … })`），换地方是"开一场之前"的动作。
局内真会变的只有烟的状态、姿势、烟灰缸身份、天气、光、以及设置里能当场改的皮肤/自定义背景。
前四样这一轮全部接上了声（拾起＝lift、磕灰与掐灭＝按盘的材质、火星＝同一个 presence、光与影＝房间增益与
暗角）；后两样按 Frozen Core 只动四层颜色，**本来就不该有声音** —— 给皮肤配音就是给装饰配音。
所以这句需求今天没有剩余的待接项。

### 55.4 点烟是一个动作：烟杆要走到火那里去（2026-10-07）

`LIGHTING` 以前只是一段计时器：状态一进去，`ignitionMs` 就开始累加，烟杆停在手上不动，
一秒钟后火就"凭空"着了。现在 `restingTarget()` 多了一条 LIGHTING 分支：
烟囱口 `flamePoint(layout)` 是归一化坐标里的一个点（`layout.lighter` 往上 0.026，
因为那个锚点是**机身**的点击中心，火在它上面），杆的端点被放到那一点上 ——
`pivot = offset(flame, -rodLength, angleDeg)`，所以无论杆烧到多短，端点都落在火里。

三个坑，都是量出来的，不是想出来的：

1. **两套距离不能混用。** 杆的摆放活在归一化平面里（`offset` / `angleBetween` 都是），
   而"端点离火多远"活在 `stageDistance` 的屏幕圆度量里（x 乘 aspect）。
   第一次实现拿 `stageDistance` 判断"杆够不够长"，390×844 上算出 reach=0.193 < rod=0.34，
   于是手根本不动，端点停在离火 0.064（**25 px**）的地方，`atFlame` 永远卡在 0.66。
   现在摆放用 `planeDistance`，接近度用 `stageDistance`，两个名字把两套度量分开写死。
2. **转向要走短的那条弧。** 手持角 -17°、够到火要 -172°，两条弧只差 5° 的终点，
   但一条把火头从桌子**下面**捅过去（实测端点 y 到 0.746，桌面在 0.64），一条从**上面**绕。
   `shortWayTo()` 取与当前角数值最近的那个表示。
3. **转得快才不像翻跟头。** 155° 慢慢转，在没有人手的画面里就是一根浮空的棍子在打转
   （t=240ms 那帧实测就是这样）。给 `PoseTarget` 加了 `angleStiffness`，
   LIGHTING 用 17/s：约 180ms 转完，之后 900ms 是"端点泡在火里"的静止段 —— 玩家看到的是伸手、等火、拿回来。

判据：`packages/game-core/src/__tests__/lighting-reach.test.ts` 三条。三次单点变异分别红
1 / 2 / 2 条：去掉点火门控（`atFlame < 0.55` 那行）只红"拖着不走就不着"那条；
去掉 LIGHTING 分支三条全红；把 `pivot` 钉在 `restPivot` 红前两条。

**这一轮放宽了两个既有判据，说清楚**：`plume-shape.test.ts` 的 `sigmaX` 上界 0.09 → 0.11、
footprint 0.5 → 0.62。原因是烟柱头一秒的出生点现在沿着"去打火机的路上"分布，实测
sigmaX 0.0947、footprint 0.499（2.5 s 处）。它们要抓的那种坏法（每颗粒子各自取噪声格）
当年量到 0.370 与 3.47 —— 两条界离故障仍然有一个数量级。另外 `tests/sessionLoop.test.ts`
等 `ash.ready` 的时限 90 s → 180 s：§22 允许一阵风在灰柱"该弹了"之前自己把它抖掉，
而这是随机事件，90 s 只够一个灰周期的运气。

58. Lighting

烟头：

local glow

烟雾：

soft scattering

环境：

subtle ambient light

不要使用大量霓虹渐变。

这一节也管"软"是怎么来的：贴图自己的衰减，不是 `ctx.filter`。而烟雾样式的 `blur` 以前**没有任何读者**
——写进状态就结束了，于是五种烟在"糊不糊"这一维上画出来完全一样。现在它决定贴图的四条 alpha 曲线
（`exp(-(r/σ)²)`，σ 随 blur 走），默认比原来更紧：原来那四条 stop 相当于 σ=0.56，现在 0.42 ——
用户说的"没对上焦"正是这件事。判据 `sprite-focus.test.ts` 量的是烘焙出来的四条 alpha：单调递减、
blur 越大则外半区的光越多、默认比旧曲线更紧，并且钉住渲染器真的把样式的 blur 传给了贴图。

2026-10-06 「背景的那个东西一直在晃」补两条判据，一条量仿真、一条量画面：
`stillness.test.ts` 钉的是 `world.wind / windDirectionDeg / smoke.turbulence` 相邻帧的变化上限
（该文件记录的两头：平滑后 0.00064 / 0.0051° / 0.0033，逐帧重掷时 0.159 / 1.27° / 0.311）。但玩家看到的不是这三个字段，
